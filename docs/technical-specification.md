# Техническое задание — Флоу WMS

Описание основных операционных флоу системы управления складом.

---

## Флоу 1: Приёмка товара (реализовано)

### Описание

На склад поступает товар. Администратор создаёт приёмку (`Receipt`) с перечнем ожидаемых позиций. После прохождения статусной цепочки `Draft → Planned → Processing → Finished` товар физически приходуется по ячейкам склада и попадает в остатки.

---

### Статусная модель

| Статус | Кто действует | Что происходит |
|--------|---------------|----------------|
| `draft` | Администратор | Создаётся приёмка, формируется список ожидаемых позиций (`items`). Позиции можно добавлять, редактировать, удалять. |
| `planned` | Администратор | Список позиций зафиксирован (доступен только просмотр). Приёмка запланирована к исполнению. |
| `processing` | Администратор + Сотрудник | Физический приём товара: обновляется `receivedCount` (фактически принятое количество), добавляются placements (размещения по ячейкам). |
| `finished` | Администратор | Приёмка завершена. Все позиции с `receivedCount` полностью размещены (плейсментов достаточно). Остатки в ячейках зафиксированы. |
| `canceled` | Администратор | Приёмка отменена. Допустимо из `draft`, `planned`, `processing` (только если нет placements). |

Допустимо вернуться назад (`revert`): `Finished → Processing`, `Processing → Planned` (если нет placements), `Planned → Draft`.

---

### Участники

| Участник             | Роль |
|----------------------|------|
| **Администратор**    | Создаёт приёмку, управляет статусами, формирует список позиций, завершает приёмку |
| **Сотрудник склада** | В статусе Processing вводит фактически принятое количество и указывает, куда разложил товар |

---

### Пошаговый флоу

#### Фаза 1 — Администратор создаёт приёмку (Draft)

1. Открывает раздел «Приёмки», нажимает «Создать».
2. Заполняет: название (опционально), причину (`newGoods` / `return` / `other`), склад, ожидаемую дату доставки, примечание.
3. Добавляет позиции через «Редактировать состав»: для каждой выбирает позицию из каталога и указывает ожидаемое количество (`plannedCount`).
4. Позиции можно редактировать пока приёмка в статусе `draft` или `planned`.

#### Фаза 2 — Перевод в Planned

1. Администратор нажимает «Запланировать» (Draft → Planned).
2. При необходимости — «Редактировать состав» ещё доступен.
3. При необходимости откатиться — «Вернуть» (Planned → Draft).

#### Фаза 3 — Начало приёмки (Processing)

1. Администратор нажимает «Начать приёмку» (Planned → Processing).
2. Теперь редактирование состава через «Редактировать позиции» недоступно. Доступны:
   - **Поиск по каталогу** — строка поиска с debounce вызывает `GET /api/catalog` с фильтром по типам `standard`, `unit`. Результаты сопоставляются с позициями приёмки:
     - Совпавшие позиции приёмки показываются в отфильтрованной таблице.
     - Товары из каталога, которых нет в приёмке, показываются отдельным блоком «Добавить в приёмку».
   - **Быстрое добавление позиции** (`POST /api/receipts/{id}/items/quick-add`) — добавляет товар из каталога в приёмку с `plannedCount=0`. Разрешены только неархивные, нелиртуальные типы (`standard`, `unit`). Используется когда при физической приёмке обнаружен незапланированный товар.
   - Обновление `receivedCount` — фактически принятое количество по каждой позиции.
   - Добавление placement — куда физически положен товар:
     - **Standard**: позиция счётного типа → выбирается ячейка и вводится количество. Поддерживается **массовое размещение** (`POST /api/receipts/{id}/placements/standard/batch`) — выбор нескольких Standard-позиций через checkbox и единовременное размещение в одну ячейку.
     - **Unit**: сериализованная единица → выбирается ячейка и вводится инвентарный номер.
   - Удаление ошибочно добавленных placements (c откатом изменений остатков).

#### Фаза 4 — Завершение (Finished)

1. Администратор нажимает «Завершить».
2. Система проверяет: все позиции с указанным `receivedCount` должны быть полностью размещены (сумма placements == receivedCount).
3. При несоответствии — ошибка 422. Позиции без `receivedCount` игнорируются в проверке.
4. Приёмка переходит в `finished`. Остатки зафиксированы.

---

### Типы размещений (placements)

| Тип | Catalog item type | Что фиксируется в inventory |
|-----|-------------------|------------------------------|
| `standard` | `standard`, `variation`, `bundle`, `productGroup` | `StoragePlaceNodeItemsGroup.Count` увеличивается |
| `unit` | `unit` | Создаётся `UnitInventoryItem` с `inventoryNumber`, привязывается к ячейке |

## Флоу 4: Списания (реализовано)

### Описание

Фиксирует выбытие товара со склада по причине потери, брака или иной причины. Операция производится в два шага: сначала формируется черновик с перечнем списываемых позиций, затем выполняется само списание (`Draft → Finished`) — товары атомарно удаляются из остатков.

---

### Статусная модель

| Статус | Что происходит |
|--------|----------------|
| `draft` | Документ создан. Список позиций можно редактировать: добавлять товары из любых ячеек склада, менять количество, удалять строки. Метаданные (название, причина, примечания) доступны для правки. |
| `finished` | Списание выполнено. Для каждой позиции атомарно вызваны операции удаления инвентаря (`RemoveStandardItemsFromNodeAsync` / `RemoveUnitItemAsync`). Остатки в ячейках уменьшены. |
| `canceled` | Документ отменён без воздействия на инвентарь. Доступно только из `draft`. |

---

### Ключевые отличия от Приёмки

- **Нет промежуточных статусов** — `Draft → Finished` без `Planned` / `Processing`.
- **Источник — несколько ячеек** — каждая строка (`WriteoffItem`) хранит свой `sourceNodeId`, одно списание может охватывать позиции из разных ячеек одного склада.
- **Нет placements** — вместо размещения производится удаление из существующего инвентаря.

---

### Причины списания

| Значение | Отображение |
|----------|-------------|
| `loss` | Потеря |
| `defect` | Брак |
| `other` | Прочее |

---

### Пошаговый флоу

#### Шаг 1 — Создание черновика

1. Пользователь открывает раздел «Списания», нажимает «Новое списание».
2. Вводит название, выбирает причину и склад, при необходимости — примечание.
3. После создания документ находится в статусе `draft`.

#### Шаг 2 — Формирование списка позиций

1. На странице документа нажимает «Редактировать» в секции «Товары».
2. В открывшемся drawer нажимает «Добавить товары из ячейки».
3. Выбирает ячейку через модальный picker (с выбором склада и узла дерева хранения).
4. После выбора ячейки открывается `InventoryItemPickerModal` с инвентарём этой ячейки — пользователь отмечает позиции и указывает количество (для стандартных товаров).
5. Операцию «выбрать ячейку → выбрать товары» можно повторить для нескольких ячеек.
6. Нажимает «Сохранить» — список сохраняется через `PUT /api/writeoffs/{id}/items`.

#### Шаг 3 — Выполнение списания

1. Нажимает «Завершить» — открывается диалог подтверждения.
2. После подтверждения вызывается `POST /api/writeoffs/{id}/finish`.
3. Сервер проверяет наличие позиций и выполняет все операции удаления в одной транзакции.
4. При нехватке товара в ячейке возвращается 422 `writeoffInsufficientInventory`.
5. Успешно — документ переходит в статус `finished`.

---

### Участники

| Участник | Роль |
|----------|------|
| **Администратор** (`writeoffs.edit`) | Полный доступ: создание, редактирование, выполнение списания на любом складе |
| **Сотрудник** (`writeoffs.edit_assigned`) | То же, но только для назначенных складов |
