# Техническое задание — Флоу WMS

Описание основных операционных флоу системы управления складом.

---

## Флоу 1: Приёмка товара

### Описание

На склад поступает товар. Администратор создаёт приёмку (`Receipt`) с перечнем ожидаемых позиций. После прохождения статусной цепочки `Draft → Planned → Processing → Finished` товар физически приходуется по ячейкам склада и попадает в остатки.

---

### Статусная модель

| Статус | Кто действует | Что происходит |
|--------|---------------|----------------|
| `draft` | Администратор | Создаётся приёмка, формируется список ожидаемых позиций (`items`). Позиции можно добавлять, редактировать, удалять. |
| `planned` | Администратор | Список позиций зафиксирован (доступен только просмотр). Приёмка запланирована к исполнению. |
| `processing` | Администратор + Сотрудник | Физический приём товара: обновляется `receivedCount` (фактически принятое количество), добавляются placements (размещения по ячейкам). |
| `finished` | Администратор | Приёмка завершена. Все позиции с `receivedCount` полностью размещены (плейсментов достаточно). Остатки в ячейках зафиксированы. |
| `canceled` | Администратор | Приёмка отменена. Допустимо из `draft`, `planned`, `processing` (только если нет placements). |

Допустимо вернуться назад (`revert`): `Finished → Processing`, `Processing → Planned` (если нет placements), `Planned → Draft`.

---

### Участники

| Участник             | Роль |
|----------------------|------|
| **Администратор**    | Создаёт приёмку, управляет статусами, формирует список позиций, завершает приёмку |
| **Сотрудник склада** | В статусе Processing вводит фактически принятое количество и указывает, куда разложил товар |

---

### Пошаговый флоу

#### Фаза 1 — Администратор создаёт приёмку (Draft)

1. Открывает раздел «Приёмки», нажимает «Создать».
2. Заполняет: название (опционально), причину (`newGoods` / `return` / `other`), склад, ожидаемую дату доставки, примечание.
3. Добавляет позиции через «Редактировать состав»: для каждой выбирает позицию из каталога и указывает ожидаемое количество (`plannedCount`).
4. Позиции можно редактировать пока приёмка в статусе `draft` или `planned`. `PUT /api/receipts/{id}/items` принимает полный желаемый состав: позиции, отсутствующие в списке, удаляются; повтор `catalogItemId` — 422 `validationError`.

#### Фаза 2 — Перевод в Planned

1. Администратор нажимает «Запланировать» (Draft → Planned).
2. При необходимости — «Редактировать состав» ещё доступен.
3. При необходимости откатиться — «Вернуть» (Planned → Draft).

#### Фаза 3 — Начало приёмки (Processing)

1. Администратор нажимает «Начать приёмку» (Planned → Processing).
2. Теперь редактирование состава через «Редактировать позиции» недоступно. Доступны:
   - **Поиск по каталогу** — строка поиска с debounce вызывает `GET /api/catalog` с фильтром по типам `standard`, `unit`. Результаты сопоставляются с позициями приёмки:
     - Совпавшие позиции приёмки показываются в отфильтрованной таблице.
     - Товары из каталога, которых нет в приёмке, показываются отдельным блоком «Добавить в приёмку».
   - **Быстрое добавление позиции** (`POST /api/receipts/{id}/items/quick-add`) — добавляет товар из каталога в приёмку с `plannedCount=0`. Разрешены только неархивные, невиртуальные типы (`standard`, `unit`). Товар, уже присутствующий в приёмке, отклоняется. Используется когда при физической приёмке обнаружен незапланированный товар.
   - Обновление `receivedCount` — фактически принятое количество по каждой позиции.
   - Добавление placement — куда физически положен товар:
     - **Standard**: позиция счётного типа → выбирается ячейка и вводится количество. Поддерживается **массовое размещение** (`POST /api/receipts/{id}/placements/standard/batch`) — выбор нескольких Standard-позиций через checkbox и единовременное размещение в одну ячейку.
     - **Unit**: сериализованная единица → выбирается ячейка и вводится инвентарный номер.
   - Удаление ошибочно добавленных placements (c откатом изменений остатков).

Массовое размещение идёт одной транзакцией в одну ячейку: все позиции батча должны быть типа Standard, повтор одного `itemId` внутри батча отклоняется.

#### Фаза 4 — Завершение (Finished)

1. Администратор нажимает «Завершить».
2. Система проверяет: все позиции с указанным `receivedCount` должны быть полностью размещены (сумма placements == receivedCount).
3. При несоответствии — ошибка 422. Позиции без `receivedCount` игнорируются в проверке.
4. Приёмка переходит в `finished`. Остатки зафиксированы.

---

### Типы размещений (placements)

| Тип | Catalog item type | Что фиксируется в inventory |
|-----|-------------------|------------------------------|
| `standard` | `standard`, `variation`, `bundle`, `productGroup` | `StoragePlaceNodeItemsGroup.Count` увеличивается |
| `unit` | `unit` | Создаётся `UnitInventoryItem` с `inventoryNumber`, привязывается к ячейке |

## Флоу 3: Перемещения

`TransfersPage` (`projectwarehouse.client/src/pages/OperationsPage/pages/TransfersPage`): выбор источника и приёмника (`LocationField`), список позиций, выполнение через `transfersExecute`.

### Модель операции

У перемещения нет документа и нет статусов — это одна операция `POST /api/transfers`, а не флоу. Тело: `fromNodeId`, `toNodeId` (обязательно отличный от источника) и минимум одна позиция. Тип позиции выводится из того, какое поле заполнено: `catalogItemId` + `count` — стандартный товар, `unitItemId` — серийная единица.

Все позиции переезжают в одной транзакции: падение на любой из них откатывает перемещение целиком. Частично выполненного перемещения не существует — иначе кладовщик не знал бы, что именно уже уехало.

Права — собственное семейство `transfers.execute` / `transfers.execute_assigned`; сущности своей у перемещения нет, поэтому правила доступа тоже нет, наследуется только сужение по назначенным складам.

### Ошибки

| Код | Когда |
|-----|-------|
| `transferSameNode` | `fromNodeId` == `toNodeId` |
| `insufficientInventory` | В ячейке-источнике не хватает стандартного товара (несёт `args`, см. [errors.md](errors.md)) |
| `storagePlaceNodeNotFound` | Не найден источник или приёмник |
| `unitInventoryItemNotFound` | Серийная единица не найдена или уже уехала |

## Флоу 4: Списания

### Описание

Фиксирует выбытие товара со склада по причине потери, брака или иной причины. Операция производится в два шага: сначала формируется черновик с перечнем списываемых позиций, затем выполняется само списание (`Draft → Finished`) — товары атомарно удаляются из остатков.

---

### Статусная модель

| Статус | Что происходит |
|--------|----------------|
| `draft` | Документ создан. Список позиций можно редактировать: добавлять товары из любых ячеек склада, менять количество, удалять строки. Метаданные (название, причина, примечания) доступны для правки. |
| `finished` | Списание выполнено. Для каждой позиции атомарно вызваны операции удаления инвентаря (`RemoveStandardItemsFromNodeAsync` / `RemoveUnitItemAsync`). Остатки в ячейках уменьшены. |
| `canceled` | Документ отменён без воздействия на инвентарь. Доступно только из `draft`. |

---

### Ключевые отличия от Приёмки

- **Нет промежуточных статусов** — `Draft → Finished` без `Planned` / `Processing`.
- **Источник — несколько ячеек** — каждая строка (`WriteoffItem`) хранит свой `sourceNodeId`, одно списание может охватывать позиции из разных ячеек одного склада.
- **Нет placements** — вместо размещения производится удаление из существующего инвентаря.

---

### Причины списания

| Значение | Отображение |
|----------|-------------|
| `loss` | Потеря |
| `defect` | Брак |
| `other` | Прочее |

---

### Пошаговый флоу

#### Шаг 1 — Создание черновика

1. Пользователь открывает раздел «Списания», нажимает «Новое списание».
2. Вводит название, выбирает причину и склад, при необходимости — примечание.
3. После создания документ находится в статусе `draft`.

#### Шаг 2 — Формирование списка позиций

1. На странице документа нажимает «Редактировать» в секции «Товары».
2. В открывшемся drawer нажимает «Добавить товары из ячейки».
3. Выбирает ячейку через модальный picker (с выбором склада и узла дерева хранения).
4. После выбора ячейки открывается `InventoryItemPickerModal` с инвентарём этой ячейки — пользователь отмечает позиции и указывает количество (для стандартных товаров).
5. Общее поле поиска над секциями фильтрует стандартные и единичные товары одновременно; при смене запроса пагинация возвращается на первую страницу.
6. Операцию «выбрать ячейку → выбрать товары» можно повторить для нескольких ячеек.
7. Нажимает «Сохранить» — список сохраняется через `PUT /api/writeoffs/{id}/items`.

Тело — полный желаемый состав, каждый элемент описывает одну строку инвентаря: `sourceNodeId` (ячейка должна принадлежать складу документа) плюс ровно один дискриминатор типа — `catalogItemId` вместе с `count` для стандартного товара либо `unitInventoryItemId` для серийного. Заполнить оба или ни одного — 422.

#### Шаг 3 — Выполнение списания

1. Нажимает «Завершить» — открывается диалог подтверждения.
2. После подтверждения вызывается `POST /api/writeoffs/{id}/finish`.
3. Сервер проверяет наличие позиций и выполняет все операции удаления в одной транзакции.
4. При нехватке товара в ячейке возвращается 422 `writeoffInsufficientInventory`.
5. Успешно — документ переходит в статус `finished`.

Возможные 422: `writeoffNotDraft` (документ не в черновике), `writeoffHasNoItems` (нечего списывать), `writeoffInsufficientInventory` (несёт `args`, см. [errors.md](errors.md)), `unitInventoryItemNotFound` (серийной единицы нет в ожидаемой ячейке). Ни одна из них ничего не коммитит.

---

### Участники

| Участник | Роль |
|----------|------|
| **Администратор** (`writeoffs.edit`) | Полный доступ: создание, редактирование, выполнение списания на любом складе |
| **Сотрудник** (`writeoffs.edit_assigned`) | То же, но только для назначенных складов |

## Флоу 5: Инвентаризация

### Описание

Сверяет учётные остатки с фактическими. Кладовщик выбирает ячейки, пересчитывает в них товар, а при проведении система приводит остатки к посчитанным значениям. Корректировки пишутся в журнал движений с отдельными action-константами, чтобы не смешиваться с реальными приходами и списаниями.

Учётный остаток **не замораживается**: он вычисляется из живых остатков в момент проведения, а в интерфейсе показывается «живым». Фактически применённая корректировка сохраняется в строке (`AppliedDelta`) — только по ней и читается завершённый документ, потому что живые остатки к тому моменту уже уехали.

---

### Статусная модель

| Статус | Что происходит |
|--------|----------------|
| `planned` | Плановая инвентаризация поставлена в календарь. Возможности те же, что у `draft`; отдельный статус нужен, чтобы отличать запланированное от начатого. Переходы вручную и в обе стороны: `POST /{id}/schedule` (`draft → planned`) и `POST /{id}/to-draft` (`planned → draft`). |
| `draft` | Формируется область: выбираются ячейки (`StocktakeNode`). Строки подсчёта редактировать нельзя. Метаданные доступны для правки. |
| `inProgress` | Идёт пересчёт. По каждой ячейке отдельно сохраняется список посчитанных позиций. Область можно менять — удаление ячейки каскадом удаляет её строки. Возврат в `draft` доступен (`/revert`), строки при этом сохраняются. |
| `finished` | Корректировки применены в одной транзакции, каждой строке проставлен `AppliedDelta`. |
| `canceled` | Документ отменён без воздействия на остатки. Доступно из `planned`, `draft` и `inProgress`. |

### Плановые инвентаризации

`Stocktake.Type` (`unscheduled` | `scheduled`) отделяет разовый пересчёт от запланированного. У плановой `PlannedDate` (`DateOnly`) обязательна — без неё документ выпал бы из календаря, ради которого плановость и заводилась; у внеплановой поле принудительно обнуляется. Документ любого типа создаётся в `draft`; плановый затем кнопкой «Запланировать» переводится в `planned`.

В `PATCH` планирование необязательное: не прислали ни одного поля — не трогается вовсе, прислали `type` — переписываются и тип, и дата. `plannedDate` в одиночку (без `type`) отбивается 422: пара правится целиком, иначе непонятно, к какому типу относится дата. Присланное планирование у документа в `inProgress` — тоже 422, а не молчаливое игнорирование. Правка планирования работает, пока документ в `planned` или `draft`. Смена типа на `unscheduled` у документа в `planned` переводит его в `draft`: статус `planned` без плановости смысла не имеет. Обратный переход (`draft` → `planned`) доступен через `POST /{id}/schedule` и требует тип `scheduled`, проставленную дату и хотя бы одну ноду в области — как и «Начать»: пустой документ в календаре бесполезен.

Сортировка списка по статусу задана явным `CASE` (`planned`, `draft`, `inProgress`, `finished`, `canceled`), а не значением enum: `Planned = 4` пронумерован последним, чтобы не перенумеровывать уже сохранённые строки.

В календарь (`GET /api/events`) документ попадает, если у него есть `FinishedAt` (тогда он стоит на этой дате) либо если он плановый и не в статусе `canceled`/`draft` (тогда — на `PlannedDate`). То есть плановая инвентаризация появляется в календаре не при создании, а только после кнопки «Запланировать». `FinishedAt` хранится в UTC, поэтому день режется со сдвигом `utcOffsetMinutes` (параметр прокидывается в `ProjectTo` и подставляется в маппинг) — иначе инвентаризация, завершённая вечером, уезжает на сутки назад. Внеплановая, таким образом, видна в календаре лишь как факт после проведения.

---

### Схема данных

`Stocktake` → `StocktakeNode` → `StocktakeItem`

**Почему область — отдельная таблица `StocktakeNode`, а не `SourceNodeId` на строке (как у `WriteoffItem`):** пустая или обнулённая оператором ячейка иначе исчезала бы из документа, и «проверено, пусто» было бы неотличимо от «не выбирали». Правило проведения итерируется по области, а не по строкам. Плюс связь `StocktakeItem → StocktakeNode` (Cascade) гарантирует, что строка не может ссылаться на ячейку вне области.

**Почему `CatalogItemId` и `InventoryNumber` лежат на строке:** у строки-излишка ссылаться не на что — `UnitInventoryItem` появится только при проведении. Плюс `UnitInventoryItemId` объявлен `SetNull`, так что удаление экземпляра другой операцией обнулило бы ссылку (у `Writeoff` эта дыра открыта: проведённое списание серийного товара теряет название).

Ограничение: `StocktakeNode.StoragePlaceNodeId` — `Restrict`, поэтому ячейку, попавшую в любую (даже завершённую) инвентаризацию, больше нельзя удалить из дерева склада.

---

### Правило «ячейка авторитетна»

Остаток, который числится в ячейке области, но не упомянут ни одной строкой документа, трактуется как «посчитано 0» и списывается. Без этого не отрабатывает главный сценарий инвентаризации — товар пропал из ячейки целиком.

Страховка: проведение возможно **только** через диалог расхождений. `GET /{id}/differences` возвращает полный план без мутаций, помечая такие позиции флагом `missingFromDocument`. Предпросмотр и проведение используют один и тот же `IStocktakeDiffCalculator`, поэтому разойтись не могут.

При проведении такие позиции дописываются в документ как строки с `CountedQuantity = 0`, проставленным `AppliedDelta` и примечанием «Не указано в документе — обнулено при проведении». Иначе списание было бы видно только в журнале движений, а завершённый документ умалчивал бы о части корректировки.

---

### Обработка серийных (Unit) товаров

Порядок операций при проведении критичен:

| № | Ситуация | Что делает система | Action |
|---|----------|--------------------|--------|
| 1 | Серийник отмечен найденным в ячейке `N`, но числится в другой ячейке того же склада | `MoveUnitItemAsync` | `inventory.stocktake_relocation` (`TransferOut` + `TransferIn`) |
| 2 | Серийник числится в `N`, но не найден (или строки нет вовсе) | `DetachUnitItemAsync` — строка `UnitInventoryItem` **не удаляется**, а открепляется от ячейки (`StoragePlaceNodeId = null`), как при сборке заказа | `inventory.stocktake_shortage` (`Out`) |
| 3 | Найден серийник, откреплённый ранее и не занятый сборкой | `ReattachUnitItemAsync` — возврат того же экземпляра без потери идентичности | `inventory.stocktake_surplus` (`In`) |
| 4 | Найден серийник, неизвестный системе | `PlaceUnitItemToNodeAsync` — создаётся новый экземпляр | `inventory.stocktake_surplus` (`In`) |

Перед списком операций собирается множество `claimedFound` — серийники, заявленные найденными где угодно в документе. Оно подавляет открепление в п.2 для экземпляра, переехавшего между двумя ячейками одной инвентаризации: иначе ячейка-источник открепила бы его раньше, чем ячейка-приёмник успела забрать.

**Ненайденные серийники остаются в БД откреплёнными и исчезают из всех складских списков.** Вернуть их можно повторной инвентаризацией (п.3). Отдельного раздела «не найдены при инвентаризации» пока нет — со временем накапливается пул невидимых экземпляров.

Отказы (422, проведение блокируется целиком):

- `stocktakeUnitItemInAnotherWarehouse` — экземпляр числится на другом складе; межскладской перенос это решение перемещения, а не пересчёта.
- `stocktakeUnitItemDetached` — экземпляр откреплён и удерживается активным `AssemblyFulfillment`. Проверка обязательна: по одному лишь `StoragePlaceNodeId = null` «не найден при инвентаризации» неотличим от «в сборке», и `Reattach` увёл бы товар из собираемого заказа.
- `stocktakeUnitCountedTwice` — один серийник заявлен найденным в двух ячейках, порядок применения стал бы неоднозначным (проверяется при сохранении строк).

---

### Стандартные товары

`counted > expected` → `AddStandardItemsToNodeAsync` (`In`, `stocktake_surplus`); `counted < expected` → `RemoveStandardItemsFromNodeAsync` (`Out`, `stocktake_shortage`); равенство → операция не вызывается. Группы в ячейке без строки снимаются целиком.

### Пошаговый флоу

#### Шаг 1 — Создание и область (`planned` / `draft`)

1. Пользователь открывает «Инвентаризации», нажимает «Новая инвентаризация», выбирает склад, тип и при желании вводит название (необязательное). Для типа «Плановая» доступно поле «Плановая дата»; документ создаётся в статусе `draft`. У плановой доступна кнопка «Запланировать» (`POST /{id}/schedule` → `planned`), у запланированной — «Вернуть в черновик» (`POST /{id}/to-draft`).
2. В секции «Ячейки» добавляет узлы через `SelectNodeModal`. Каждое изменение шлёт полный список в `PUT /api/stocktakes/{id}/nodes`.
3. Одну и ту же ячейку можно добавить в любое число инвентаризаций — планировать работу наперёд это не мешает. Инвариант уже: две инвентаризации в статусе `inProgress` не могут делить ячейку. Проверяет это `FindNodeCountedElsewhereAsync` в двух точках — на `POST /start` по всей области и на `PUT /nodes` по добавленным ячейкам, если документ уже начат (без второй точки проверку обходили бы, расширив область после старта). Отказ — 422 `stocktakeNodeAlreadyInProgress` (`args.nodeId`, в тексте — имя ячейки). Два одновременных пересчёта одной ячейки подрались бы при проведении.
4. «Начать» → `POST /start`, статус `inProgress`, проставляется `StartedAt`. Стартует как из `draft`, так и из `planned` — в день плановой инвентаризации разжаловывать её в черновик не надо. `revert` всегда возвращает в `draft`, не в `planned`.

#### Шаг 2 — Пересчёт (`inProgress`)

1. Оператор раскрывает аккордеон ячейки — лениво загружается `GET /{id}/nodes/{nodeId}/stock`. Остаток ячейки отдаёт этот эндпоинт документа, а не инвентарные, поэтому экран пересчёта не требует никаких прав на склады — достаточно `stocktakes.*`.
2. Строки строятся слиянием живого остатка и уже сохранённых строк: по умолчанию факт равен учёту, поэтому трогать нужно только расхождения. Сохранённые строки без живого аналога дописываются в конец — это внесённые ранее излишки.
3. Стандартные позиции считаются числовым полем (`min = 0`), серийные — галкой «Найден». Товар, которого в ячейке нет, добавляется кнопкой «Добавить товар (излишек)».
4. «Сохранить» → `PUT /{id}/nodes/{nodeId}/items`. Синк идёт по одной ячейке, поэтому аккордеоны сохраняются независимо и два оператора не затирают друг друга. Валидация строк (префикс поля `items[i]`): тип товара из каталога должен совпадать с `kind`, среди стандартных строк не должно быть повторов `catalogItemId`, среди серийных — повторов пары `(catalogItemId, inventoryNumber)`, а разрезолвленный серийник обязан принадлежать складу документа (422 `stocktakeUnitItemInAnotherWarehouse` — та же ошибка ловится и на проведении).
5. `ValidateUnitsAgainstDocumentAsync` не даёт засчитать один серийник дважды — ни в двух ячейках одного документа, ни в другой инвентаризации со статусом `inProgress` (422 `stocktakeUnitCountedTwice`, в `args` — `stocktakeId` и `stocktakeNumber` конфликтующего документа; он может быть на чужом складе, куда текущему оператору хода нет, поэтому id нужен для ссылки тем, у кого доступ есть). Проверка стоит до резолва экземпляра, поэтому ловит и излишки с ещё несуществующим номером — иначе оба документа попытались бы создать экземпляр. Без неё побеждал бы тот, кто провёлся позже, а второй документ навсегда сохранил бы ложную недостачу. Проверка идёт на каждом сохранении ячейки и бьёт по всей истории строк, поэтому под неё есть индекс `IX_StocktakeItems_InventoryNumber` (миграция `AddStocktakeItemInventoryNumberIndex`). Это не защита от гонки: два одновременных сохранения увидят чисто оба — уникального индекса на строках нет.

#### Шаг 3 — Проведение

1. «Завершить» открывает диалог расхождений (`GET /{id}/differences`) со сводкой излишков, недостач и перемещений.
2. Позиции с `missingFromDocument` подсвечены и подписаны «нет в документе — будет списано». Непроводимые ситуации выводятся отдельным блоком и блокируют кнопку.
3. `POST /{id}/finish` внутри execution strategy и транзакции перечитывает агрегат, заново строит план и применяет его. Статус `finished`, `FinishedAt`, `AppliedDelta` на каждой строке.

---

### Известное ограничение

Учётный остаток пересчитывается в момент проведения — между пересчётом и проведением остаток может измениться сторонней операцией, и корректировка применится от свежего значения. `AppliedDelta` и предпросмотр закрывают видимость, но не саму гонку. Рекомендация: не оперировать ячейками, пока по ним идёт инвентаризация.
