# Спецификация real-time-обновлений

## Обзор

Инфраструктура доставки событий с сервера в браузер без опроса. Общая для всего приложения: первым потребителем становится статус синхронизации маркетплейсов (см. [marketplaces-specification.md](marketplaces-specification.md)), следующим — блокировки объектов, редактируемых другим пользователем.

Транспорт — **Server-Sent Events**: один долгоживущий `GET`-стрим, по которому сервер шлёт события. Команды (захват блокировки, продление, освобождение) остаются обычными REST-эндпоинтами.

### Главный принцип

**События — это подсказки к обновлению, а не источник истины.**

Клиент, получив событие, инвалидирует соответствующий запрос TanStack Query и перечитывает состояние обычным REST-вызовом. Из этого следует всё остальное:

- порядок доставки не гарантируется и не требуется;
- потерянное событие не ломает данные — следующее (или ручное обновление) приведёт состояние в порядок;
- переподключение не нуждается в проигрывании пропущенного: клиент просто перечитывает то, что видит на экране;
- сервер не обязан хранить историю событий.

Ровно поэтому в схеме нет ни буфера воспроизведения, ни `Last-Event-ID`, ни подтверждений доставки. Попытка сделать SSE источником истины вернула бы всю эту сложность.

## Почему SSE

| | SSE | SignalR | Голый WebSocket |
|---|---|---|---|
| Типы в существующем пайплайне кодогенерации | ✓ | — | — |
| Новые зависимости на фронтенде | нет | `@microsoft/signalr` | нет |
| Направление | сервер → клиент | двустороннее | двустороннее |
| Переподключение | из коробки | из коробки | пишется вручную |
| Передача JWT | заголовок `Authorization` | query string | query string |

**Кодогенерация.** `@hey-api/openapi-ts` уже генерирует SSE-обвязку — `src/api/core/serverSentEvents.gen.ts` с `onSseEvent`, `onSseError` и повторными подключениями. Она построена на `fetch`, а не на нативном `EventSource`, поэтому проходит через существующие интерцепторы `src/services/apiClient.ts` вместе с заголовком `Authorization`. Эндпоинт, описанный в OpenAPI, превращается в типизированную SDK-функцию тем же `npm run generate-api`, что и всё остальное.

**Двусторонность не нужна.** Команды блокировок обязаны проходить проверку прав, возвращать `AppProblemDetails` и попадать в OpenAPI — им место в REST, а не в канале сообщений. Двусторонний транспорт здесь не добавляет возможностей, а уводит команды из-под общего пайплайна валидации и ошибок.

**Мгновенное освобождение блокировки при закрытии вкладки** — единственное, что SignalR даёт даром через `OnDisconnectedAsync`, — воспроизводится на SSE: соединение имеет идентификатор, обрыв стрима детектируется по `HttpContext.RequestAborted`, все блокировки этого соединения снимаются.

> **Когда решение стоит пересмотреть:** если появится высокочастотный двусторонний обмен — совместное редактирование, курсоры пользователей, чат. Для уведомлений и блокировок SignalR избыточен и стоит выпадения из кодогенерации.

Голый WebSocket не рассматривается: переподключение, heartbeat, группы и backpressure пришлось бы писать вручную — именно то, за что отвечает SignalR.

## Транспорт

### Стрим

```
GET /api/realtime/stream
Accept: text/event-stream
Authorization: Bearer <access token>
```

Требует только `[Authorize]` — отдельного права на сам стрим нет. Фильтрация выполняется на уровне подписок: соединение получает только события тех объектов, на которые оно явно подписалось через `watch`, а право проверяется в момент подписки (см. «Реестр наблюдателей»).

Первым сообщением приходит `connectionReady` с идентификатором соединения — он нужен командам блокировок:

```
event: message
data: {"id":"...","type":"connectionReady","at":"...","payload":{"connectionId":"..."}}
```

### Требования к ответу

```csharp
Response.Headers.ContentType  = "text/event-stream";
Response.Headers.CacheControl = "no-cache";
Response.Headers["X-Accel-Buffering"] = "no";   // отключает буферизацию на обратном прокси
HttpContext.Features.Get<IHttpResponseBodyFeature>()?.DisableBuffering();
```

Без `DisableBuffering()` Kestrel копит ответ и события приходят пачками с задержкой.

### Keep-alive

Раз в 20 секунд в стрим уходит SSE-комментарий `:ping`. Прокси и мобильные сети рвут соединения, которые молчат; комментарий игнорируется клиентом, но держит канал живым.

### Время жизни и токен

Access-токен живёт 15 минут, `ClockSkew` равен нулю — стрим переживает собственную авторизацию. Решение: **сервер закрывает стрим по истечении токена**, клиент переподключается с уже обновлённым токеном (интерцептор `apiClient.ts` обновляет его проактивно за 30 секунд до истечения).

Альтернатива — валидировать токен только при установке соединения — отвергнута: отозванный доступ продолжал бы получать события часами, а `SecurityVersion`-инвалидация JWT перестала бы работать для стрима.

### Одно соединение на вкладку

HTTP/1.1 ограничивает браузер шестью соединениями на источник, и висящий стрим занимает одно из них. Поэтому стрим ровно один на всё приложение — им владеет `RealtimeProvider`, а не отдельные компоненты.

> **Ограничение:** несколько открытых вкладок съедают по соединению каждая. При HTTP/2 это неважно, но dev-прокси Vite работает по HTTP/1.1 — при отладке с 5+ вкладками запросы начнут вставать в очередь. Разделение одного стрима между вкладками через `BroadcastChannel` — возможное развитие, в первую версию не входит.

### Capacitor

Android-приложение уходит в фон — стрим рвётся. `RealtimeProvider` переподключается по событию `resume` и инвалидирует активные запросы: за время в фоне могло измениться что угодно. Источник `capacitor://localhost` уже разрешён политикой CORS `CapacitorPolicy`.

## Схема событий

Общий конверт:

```
RealtimeEvent
├── Id        — Guid, идентификатор события
├── Type      — RealtimeEventType, строковый enum
├── At        — DateTime, UTC
└── Payload   — полезная нагрузка, зависит от Type
```

Каталог событий первой версии:

| `Type` | Когда | `Payload` | Статус |
|--------|-------|-----------|--------|
| `connectionReady` | Установлено соединение | `{ connectionId }` | ✓ |
| `marketplaceSyncProgress` | Сохранена очередная страница синхронизации | `{ accountId, syncRunId }` | ✓ |
| `marketplaceSyncFinished` | Синхронизация завершена | `{ accountId, syncRunId, status }` | ✓ |
| `editLockAcquired` | Объект заблокирован | `{ entityType, entityId, userId, userName, expiresAt }` | ✓ |
| `editLockReleased` | Блокировка снята | `{ entityType, entityId, userId, userName }` | ✓ |
| `entityChanged` | Объект изменён и сохранён | `{ entityType, entityId, byUserId, byUserName }` | ✓ |
| `entityPresenceChanged` | Изменился состав смотрящих на объект | `{ entityType, entityId, viewers: [{ userId, userName }] }` | ✓ |

**В `editLockReleased` держатель всё-таки едет** — вопреки первоначальной схеме `{ entityType, entityId }`.
Событие служит запасным триггером устаревания, а значит клиент обязан отличать чужое освобождение от
собственного; имя нужно тому же баннеру, что и `staleBy`.

**Счётчиков в `marketplaceSyncProgress` нет.** По главному принципу документа событие — подсказка: клиент инвалидирует `/sync-runs` и перечитывает счётчики оттуда. Дублировать их в payload значило бы править схему события каждый раз, когда в `MarketplaceSyncRun` появляется новый счётчик — у заказов их уже четыре. `status` в `marketplaceSyncFinished` оставлен: по нему показывается тост, не дожидаясь refetch.

**Именование — camelCase, как у всех остальных enum'ов проекта.** Точечные имена (`marketplace.sync.progress`) потребовали бы `[JsonStringEnumMemberName]` на каждом члене и правки схемного трансформера в `Program.cs`, который строит enum из `Enum.GetNames` с camelCase-политикой: схема и провод разъехались бы. Плоские имена конфликтов не порождают — префикс области остаётся в самом имени.

### Типизация payload

`Payload` — полиморфный тип System.Text.Json: `[JsonPolymorphic(TypeDiscriminatorPropertyName = "type")]` на абстрактной базе и `[JsonDerivedType]` на каждом варианте. `Type` конверта **вычисляется** из payload (`Type => Payload.Type`), поэтому разъехаться они не могут; каждое переопределение помечено `[JsonIgnore]`, иначе STJ падает на конфликте с именем дискриминатора.

Дискриминатор при этом дублируется — `type` на конверте и `type` внутри `payload`. Это цена сериализации union'а: STJ пишет дискриминатор только внутрь полиморфного объекта.

**Проверено на живом эндпоинте:** `@hey-api/openapi-ts` разворачивает такой union корректно. `RealtimeEventPayload` генерируется как TS-union из пересечений `{ type?: "marketplaceSyncProgress" } & …`, сужение по `payload.type` работает — `tsc` принимает доступ к полям конкретного варианта внутри соответствующей ветки. Запасной вариант с `JsonElement` и ручным разбором не понадобился.

## Серверная часть

```
Infrastructure/Realtime/
├── IRealtimeNotifier.cs          — публикация событий
├── RealtimeConnectionManager.cs  — singleton, реестр соединений
├── RealtimeEvent.cs              — конверт
├── RealtimeEventType.cs          — enum типов
├── RealtimeAddress.cs            — адресация
├── EntityWatchRegistry.cs        — кто на какой объект сейчас смотрит
└── EntityPresenceService.cs      — тот же реестр, но в людях, а не в соединениях

Services/
└── IEntityAccessService.cs       — AppEntityType → право просмотра/редактирования
```

### Публикация

```csharp
public interface IRealtimeNotifier
{
    ValueTask PublishAsync(RealtimeAddress address, RealtimeEvent evt, CancellationToken ct = default);
}
```

Регистрируется как singleton — публиковать события должны и scoped-сервисы контроллеров, и Quartz-джобы, живущие вне HTTP-запроса.

### Адресация

```csharp
RealtimeAddress.ToUser(Guid userId)
RealtimeAddress.ToWatchers(AppEntityType entityType, Guid entityId, Guid? exceptUserId = null)
RealtimeAddress.ToAll()
```

`exceptUserId` — то самое исключение автора для `entityChanged`. Оно живёт в адресе, а не в перегрузке
`IRealtimeNotifier.PublishAsync`: фильтрация по получателю — свойство адресации, и существующие вызовы от
опционального параметра не меняются.

`ToWatchers` — **основной и единственный способ адресации объектных событий**: `entityChanged`, `editLock*` и события синхронизации маркетплейсов. Событие уходит только тем соединениям, которые явно объявили интерес к этому объекту.

`ToUser` — для персональных уведомлений, не привязанных к объекту. `ToAll` — для глобальных (перезапуск сервера, общий баннер); потребителей в первой версии нет, метод заводится как точка расширения.

**`ToPermission` намеренно не существует.** Событий, адресуемых «всем, у кого есть право X», в схеме не осталось: единственный кандидат — синхронизация маркетплейсов — адресуется наблюдателям аккаунта (`ToWatchers(MarketplaceAccount, accountId)`), а это и точнее, и дешевле. Отказ от неё убирает необходимость фиксировать клеймы `permission` на соединении и сверять их на каждой публикации.

### Что хранит соединение

На `RealtimeConnection` фиксируются только `UserId` и `UserName`:

- `UserId` — для `ToUser`, для исключения автора из `entityChanged` и для снятия его блокировок по обрыву;
- `UserName` — попадает в payload `editLockAcquired`, чтобы не ходить в БД на каждый захват.

Клеймы `permission` на соединении не хранятся. Все проверки прав происходят в обычных HTTP-запросах (`watch`, `locks/acquire`), где есть живой `ClaimsPrincipal` из токена; на публикации события права не проверяются вовсе — фильтр уже сделан подпиской.

Протухшие подписки самолечатся: отзыв права бампает `SecurityVersion`, стрим закрывается на следующей проверке токена, клиент переподключается и **заново шлёт `watch`** — который уже не проходит по свежим клеймам. Окно между отзывом права и закрытием стрима (до 15 минут) существовало бы и с `ToPermission`: там клеймы фиксировались при установке соединения и устаревали ровно так же.

### Реестр наблюдателей

`EntityWatchRegistry` — singleton с `ConcurrentDictionary<(AppEntityType, Guid), HashSet<Guid>>`, где значение — идентификаторы соединений.

```
POST /api/realtime/watch     — { connectionId, entities: [{ entityType, entityId }] }  → { watched: [...] }
POST /api/realtime/unwatch   — { connectionId, entities: [{ entityType, entityId }] }  → 204
```

**Подписки батчатся** — вопреки первоначальной схеме «один объект на запрос». Экран подписывается на каждый
видимый объект: список сборки открывал бы по запросу на заказ прямо на монтировании, при лимите браузера в шесть
соединений на источник. Клиент собирает все `watch`/`unwatch`, зарегистрированные за один рендер, в один вызов.

Отсюда и ответ: `watch` возвращает `200 { watched }` вместо `204`. Отказ по правам теперь **поштучный** —
объект, который пользователю не виден, просто отсутствует в списке, и один запрещённый объект не топит весь
батч. Отдельного `403` у эндпоинта больше нет.

Проверка прав осталась поштучной, по одному запросу к БД на объект: батчить её не стали — рядом уже есть
кэширование, а выигрыш давал именно отказ от лишних HTTP-запросов.

Блокировки батчинга не получают: их берёт форма, а не экран, — у них свой однообъектный `RealtimeLockRequest`.

Право на просмотр объекта проверяется **один раз при подписке**, а не на каждом событии. Это избавляет от широковещательной рассылки: соединение, не подписанное на объект, о его изменениях не узнаёт вовсе.

Отображение `AppEntityType → право просмотра` живёт не в инфраструктуре real-time, а в `Services/IEntityAccessService.cs` — там же место для будущих неполных проверок (доступ к конкретному складу, фильтр `IUserQueryFilterService`), которых карта прав сама по себе не покрывает:

```csharp
public interface IEntityAccessService
{
    Task<bool> CanViewAsync(AppEntityType entityType, Guid entityId, ClaimsPrincipal user, CancellationToken ct = default);
    Task<bool> CanEditAsync(AppEntityType entityType, Guid entityId, ClaimsPrincipal user, CancellationToken ct = default);
}
```

**Реализовано.** Сервис — тонкий фасад над `Infrastructure/Access/EntityAccessRegistry`, где живёт карта «тип сущности → право» целиком; тем же реестром пользуются фильтры списков и пообъектные проверки в контроллерах (см. [permissions.md](permissions.md#where-access-is-checked)). `AppEntityType` без зарегистрированного правила даёт `false`: подписка на то, чего инфраструктура не знает, невозможна.

`CanEdit` используется захватом блокировки — требование «то же право, что и редактирование объекта» перестаёт быть продублированным в контроллере блокировок.

**`CanEdit(Order)` — это `orders.edit | orders.edit_assigned`, без `orders.assemble_assigned`.** У заказа несколько `AssemblyTask`, каждое со своим `AssignedToId`: одновременная работа нескольких сборщиков — штатный сценарий, а не гонка. Эксклюзивная блокировка показала бы им ложное «редактирует Иванов» на обычной параллельной сборке. `CanView(Order)`, напротив, `assemble_assigned` включает — сборщик обязан иметь возможность подписаться на заказ, который собирает.

Отсюда следствие для экрана сборки (`/operations/assembly`): он берёт `useEntityWatch`, но **не** `useEditLock`. Двум сборщикам как раз нужно видеть фулфилменты друг друга через `entityChanged`.

Подписка снимается при `unwatch`, при обрыве стрима (вместе с блокировками этого соединения) и при закрытии соединения по истечении токена. Захват блокировки подписку **не заменяет**: страницу объекта открывают и те, кто её не редактирует.

### Presence

«Этот объект просматривают …» — надстройка над тем же реестром, без собственной структуры данных.
`EntityPresenceService` переводит соединения в людей (`DistinctBy(UserId)`) и владеет всеми мутациями
`EntityWatchRegistry`: только так момент публикации совпадает с моментом изменения **дедуплицированного**
списка. Вторая вкладка того же человека события не порождает — состав смотрящих не изменился.

**Событие несёт полный список, а не дельту join/left.** Это единственное событие схемы, которому нечего
перечитывать: presence не хранится нигде, кроме памяти сервера, и REST-эндпоинта для него нет. Поэтому оно
обязано быть тем состоянием, о котором сообщает, а не подсказкой к чтению. Соответственно, потеря события
здесь не самолечится через refetch — она чинится следующим приходом или уходом наблюдателя. Цена приемлема:
presence ничего не решает, а список из четырёх аватарок — не данные, за которые бьются.

**Начальный список едет в ответе `watch`** (`{ watched, presence }`). Иначе страница показывала бы «никого» до
первого чужого прихода — то самое окно «подписался, но событие уже ушло», только закрыть его повторным
чтением нельзя.

Имя — `FullName`, а не логин: соединение берёт его из клеймов `given_name`/`family_name` токена, поэтому
поход в БД не нужен, а `EditLockBanner` и `StaleDataBanner` получают человеческое имя заодно — они читают то
же поле `userName`.

`RemoveConnectionAsync` вызывается **после** `connections.Remove`, иначе умирающий стрим получал бы прощание
о самом себе в уже закрытый канал.

### Реестр соединений

`RealtimeConnectionManager` — singleton с `ConcurrentDictionary<Guid, RealtimeConnection>`. Каждое соединение владеет `Channel<RealtimeEvent>` **ограниченной ёмкости** (64) с режимом `BoundedChannelFullMode.Wait`.

Переполнение канала означает, что клиент не успевает читать. Реакция — закрыть соединение, а не копить события: клиент переподключится и перечитает состояние через REST. Главный принцип документа делает это безопасным — события всё равно не источник истины.

Режим `Wait`, а не `DropWrite`, именно ради обнаружимости: при `DropWrite` неблокирующий `TryWrite` возвращает `true` и молча теряет событие, то есть застрявший читатель ничем себя не выдаёт. При `Wait` полный буфер даёт `false` — и это тот самый сигнал, по которому соединение закрывается.

Реестр в памяти согласован с текущим однонодовым допущением проекта: `SecurityVersionStore` уже документирован как не multi-instance safe.

> **Планируется:** при переходе на несколько инстансов нужен backplane — событие, опубликованное на одной ноде, должно дойти до соединений на других. Дешёвый вариант при уже имеющемся PostgreSQL — `LISTEN`/`NOTIFY` через Npgsql, без добавления Redis. В первую версию не входит.

## Блокировки редактирования

### Область ответственности

**Блокировка носит уведомительный характер: она сообщает, что объект сейчас кто-то редактирует, и ничего не запрещает.** Сохранение не блокируется, форма не переводится в режим только для чтения — пользователь видит предупреждение и решает сам.

Это осознанный выбор. Из него следует, что механизм **не защищает данные от конкурентной записи**: два пользователя, открывшие одну форму, по-прежнему перезаписывают изменения друг друга, побеждает последний сохранивший. Блокировка лишь делает ситуацию заметной до того, как она произошла, — в подавляющем большинстве случаев человек, увидев «редактирует Иванов», просто не станет сохранять.

Токен конкурентности (`UseXminAsConcurrencyToken` — системная колонка PostgreSQL, не требует изменений схемы) — то, что закрыло бы дыру по-настоящему, — вынесен в «Отложено». Порядок при возврате к нему: сначала токен, потом ужесточение интерфейса, иначе форма начнёт обещать безопасность раньше, чем та появится.

### Модель

Ключ блокировки универсален — пара, которая уже используется в changelog:

```
EditLock
├── EntityType    — AppEntityType
├── EntityId      — Guid
├── UserId        — Guid
├── UserName      — string, для отображения «редактирует Иванов»
├── ConnectionId  — Guid, соединение-владелец
├── AcquiredAt    — DateTime
└── ExpiresAt     — DateTime
```

Хранится в памяти (`ConcurrentDictionary<(AppEntityType, Guid), EditLock>`), не в БД. Блокировка живёт десятки секунд и не переживает перезапуск приложения — персистентность ей не нужна, а запись в БД на каждый heartbeat создала бы постоянный поток обновлений.

Использовать advisory-локи PostgreSQL здесь нельзя: они привязаны к сессии базы, а не к пользователю приложения.

### API

| Метод | Путь | Назначение |
|-------|------|------------|
| `POST` | `/api/realtime/locks/acquire` | Захват: `{ entityType, entityId, connectionId }` |
| `POST` | `/api/realtime/locks/heartbeat` | Продление |
| `POST` | `/api/realtime/locks/release` | Освобождение |

Отдельного эндпоинта чтения состояния нет. Признак «занято» показывается **только на странице объекта**, а туда состояние приходит само: `acquire` при неудаче возвращает `409 editLockHeld` с именем держателя, а последующее освобождение прилетает событием `editLockReleased`. Пакетное чтение состояния по списку объектов не заводится — оно понадобилось бы только для значков в таблицах, которых не будет.

Захват требует **того же права, что и редактирование объекта** — проверка идёт через `IEntityAccessService.CanEditAsync`. Блокировка не заменяет авторизацию и не выдаёт доступ: пользователь, не имеющий права на редактирование заказа, не может ни заблокировать его, ни узнать что-либо сверх факта «занято».

TTL — 60 секунд, heartbeat — каждые 20. Три пропущенных подряд освобождают объект.

### Освобождение

1. Явный `release` при уходе со страницы.
2. Истечение TTL.
3. Обрыв SSE-стрима: `HttpContext.RequestAborted` снимает **все** блокировки и подписки этого `ConnectionId`. Это и есть замена `OnDisconnectedAsync`.

TTL обязателен именно как страховка: закрытая по питанию вкладка не должна блокировать объект навсегда.

**Само по себе истечение события не порождает** — и этого недостаточно: чужой баннер провисел бы до перезагрузки страницы. Поэтому заведён `EditLockSweeper` — `BackgroundService` с `PeriodicTimer` на 10 секунд, который снимает просроченные блокировки и публикует по каждой обычный `editLockReleased`. Так все три способа освобождения выглядят на проводе одинаково.

### Повторный захват тем же пользователем

Тот же пользователь с **другого** соединения (открыл вторую вкладку) получает блокировку — она переносится на новое соединение с обновлением `ConnectionId`. Запрещать бессмысленно: человек конкурирует сам с собой, и отказ выглядел бы как поломка.

Другой пользователь получает `409 editLockHeld` с `args` `{ userId, userName, expiresAt }` — интерфейс показывает, кто именно держит объект и до какого момента.

### Коды ошибок

| Код | HTTP | Когда |
|-----|------|-------|
| `editLockHeld` | 409 | Объект заблокирован другим пользователем |
| `editLockNotHeld` | 409 | `heartbeat`/`release` для чужой или истёкшей блокировки |
| `realtimeConnectionUnknown` | 422 | `connectionId` не существует или уже закрыт |

`409 editLockHeld` возвращается только на `acquire` и не мешает сохранению: `PUT` объекта проверку блокировки не выполняет.

## Устаревание данных

Блокировка решает половину задачи: пока чужой баннер висит, пользователь знает, что объект занят. Но как только баннер исчезает, на экране остаются данные, загруженные **до** чужого сохранения, — и об этом ничто не сообщает. Вторая половина — предупреждение о том, что показанное могло устареть.

### Триггеры

Основной сигнал — **факт сохранения**, а не снятие блокировки:

1. **`entityChanged`** — объект действительно изменён и сохранён другим пользователем. Точный сигнал.
2. **`editLockReleased`**, если блокировку держал другой пользователь, — запасной. Срабатывает, когда изменение не породило `entityChanged`: правка затронула сущность без зарегистрированного changelog-сервиса, или объект редактировали в обход блокировки.

Оба триггера ставят один и тот же флаг. Разница в тексте не нужна — пользователю в обоих случаях сообщается одно: данные могли устареть.

Почему одного `editLockReleased` недостаточно: он означает «человек ушёл со страницы», а не «данные изменились». Держал блокировку и ничего не сохранил — предупреждение окажется ложным; сохранил, не отпуская блокировку, — предупреждения не будет вовсе. Ложные срабатывания приучают игнорировать баннер, поэтому основным сигналом он быть не может.

### Точка публикации

`entityChanged` публикуется из `AbstractChangeLogService.CompareAndSaveToChangelog`. Причины ровно там:

- метод уже принимает `(AppEntityType entityType, Guid entityId)` — тот же ключ, по которому адресуются наблюдатели;
- он уже знает действующего пользователя из клейма `sub` через `IHttpContextAccessor` — есть чем заполнить `byUserId`;
- он **не пишет запись, когда сравнение не выявило изменений**, — событие не уйдёт на сохранение, ничего не поменявшее;
- одна инъекция `IRealtimeNotifier` покрывает сразу все сущности, у которых есть changelog-сервис, вместо правки каждого контроллера.

Событие адресуется `ToWatchers(entityType, entityId)` и **не отправляется автору изменения** — свои же правки не должны объявляться устаревшими.

> **Ограничение:** покрытие ограничено сущностями с зарегистрированным `IChangeLogService<T>` — сейчас это `User`, `Roles`, `Warehouse`, `CatalogItem`, `StoragePlaceNode`, `Receipt`, `Writeoff`, `Stocktake`, `MarketplaceAccount`, `MarketplaceCard`. Всё остальное покрывается только запасным триггером.

**У заказов changelog-сервиса нет** — вопреки тому, что здесь утверждалось раньше. Публикация для них идёт из
фильтра `[PublishesEntityChanged(AppEntityType.Order)]` на `OrdersController`: он поднимает событие после любого
успешного мутирующего экшена, у которого в маршруте есть `id`. Двадцать с лишним точек вызова в контроллере —
это двадцать с лишним шансов забыть одну; батч-эндпоинты (`batch-self-assign`, `batch-fulfill`) `id` в маршруте
не имеют и публикуют по списку затронутых заказов явно.

Без этого экран сборки — ровно тот потребитель, ради которого `entityChanged` и заводился, — не получил бы
ничего: блокировок там нет, а значит нет и запасного триггера.

Синхронизация маркетплейсов changelog намеренно не использует (см. [marketplaces-specification.md](marketplaces-specification.md)) — поток событий `entityChanged` она не создаёт.

### Поведение интерфейса

Флаг устаревания приводит к одному из двух исходов:

| Состояние формы | Поведение |
|-----------------|-----------|
| Не изменена (`isDirty === false`) | Данные перечитываются автоматически, баннер не показывается |
| Изменена | Показывается `StaleDataBanner` с кнопкой «Обновить»; введённое сохраняется до явного действия |

Разделение обязательно: автоматическое обновление изменённой формы стёрло бы уже введённые данные — то есть предупреждение о потенциальной потере само стало бы её причиной. Решение о том, что важнее — свежие данные или набранный текст, — остаётся за человеком.

Баннеры взаимоисключающие и сменяют друг друга на одном месте:

```
блокировка захвачена другим  →  EditLockBanner    «Редактирует Иванов»
блокировка снята + флаг       →  StaleDataBanner   «Иванов сохранил изменения. Данные могли устареть»
```

Флаг снимается обновлением данных или явным закрытием баннера. Повторное `entityChanged` поднимает его снова.

## Фронтенд

```
src/contexts/Realtime/
├── RealtimeContext.ts
└── RealtimeProvider.tsx     — единственный стрим, переподключение, раздача событий

src/hooks/
├── useRealtimeEvent.ts      — подписка на тип события
├── useEntityWatch.ts        — watch/unwatch объекта на время жизни страницы
├── useEditLock.ts           — захват, heartbeat, освобождение, флаг устаревания
└── useEntityPresence.ts     — кто ещё смотрит на объект

src/components/
├── EditLockBanner.tsx       — «Редактирует Иванов»
├── StaleDataBanner.tsx      — «Данные могли устареть» + «Обновить»
└── EntityViewers.tsx        — аватарки тех, кто смотрит на объект
```

`RealtimeProvider` монтируется в `MainLayout` — стрим нужен только авторизованному пользователю. Он держит соединение, переподключается с экспоненциальной задержкой и раздаёт события подписчикам.

Обновление данных идёт не через состояние компонентов, а через инвалидацию кэша:

```ts
useEntityWatch("marketplaceAccount", accountId);

useRealtimeEvent("marketplaceSyncProgress", (e) => {
  queryClient.invalidateQueries({
    queryKey: marketplacesGetSyncRunsQueryKey({path: {id: e.accountId}}),
  });
});
```

Это заменяет `refetchInterval` на страницах, где он был заведён ради живых статусов.

`useEntityWatch(entityType, entityId)` подписывает соединение на события объекта при монтировании и отписывает при размонтировании. Нужен и на страницах, где ничего не редактируют, — просмотр тоже должен узнавать об изменениях, — и вне страниц объекта: модалка синхронизации заказов подписывается на каждый выбранный аккаунт на время своей жизни.

#### Подписался — перечитал

Между решением клиента жить на событиях и фактической регистрацией подписки на сервере есть окно. Прогон, завершившийся внутри него, отправит `marketplaceSyncFinished` в пустой набор наблюдателей, и на экране навсегда останется `Running` со старыми счётчиками. Окно открывается в трёх местах: `POST /sync` вернул `202`, а `watch` ещё не ушёл; страница смонтировалась под конец чужого прогона; стрим переподключился и `watch` по новому `connectionId` в полёте.

Правило, закрывающее все три: **объект попал в `watched` → инвалидировать его запросы.** Любое изменение до регистрации подписки ловится чтением, которое идёт строго после неё. Это прямое следствие главного принципа документа, и относится оно к повторному `watch` после переподключения тоже.

Отдавать текущее состояние прямо в ответе `watch` — нет: инфраструктуре подписок пришлось бы знать, как читать каждый тип сущности, а от пакетного чтения состояния документ отказался отдельным решением. Серверу правило ничего не стоит — `watch` идемпотентен, повторный вызов с теми же параметрами возвращает тот же `watched` и наблюдателя не задваивает.

По той же причине условие включения опроса — «стрим не установлен **или** подписка ещё не подтверждена», а не только «стрим оборван».

#### Устаревание — отдельный хук

`isStale` живёт не в `useEditLock`, а в самостоятельном `useStaleData(entityType, entityId, { isDirty, dataUpdatedAt, onRefresh })`, поверх которого `useEditLock` и построен.

Причина: страница может иметь редактируемую форму, но не иметь права на блокировку. `CanEdit(Order)` не включает `assemble_assigned` — сборщик блокировку не получит, а значит по исходной схеме не получил бы и предупреждения об устаревании. Разделение возвращает его на место; публичный контракт `useEditLock` при этом не меняется — он реэкспортирует весь результат `useStaleData`.

**Флаг гасится сам.** `isStale` вычисляется как `dataUpdatedAt < staleAt`, а не хранится булевым: у проекта `staleTime` равен нулю, а TanStack рефетчит активные запросы на `visibilitychange` и `online` — чтение, случившееся после события, уже ответило на предупреждение. Страница для этого отдаёт `dataUpdatedAt` своего запроса. Отдельного механизма сброса не требуется.

#### Блокировка

`useEditLock(entityType, entityId, { isDirty, dataUpdatedAt, onRefresh, enabled })` захватывает блокировку, шлёт heartbeat по интервалу, освобождает при размонтировании и на `beforeunload`, а после переподключения стрима захватывает заново под новым `connectionId` — старую сервер уже снял по обрыву. Подписку выполняет сам, вызывая `useStaleData` внутри. Возвращает:

```ts
{
  isOwner: boolean;
  heldBy: {userId: string; userName: string} | null;
  isStale: boolean;
  staleBy: {userId: string; userName: string} | null;
  isLoading: boolean;
  refresh: () => void;      // инвалидация запросов объекта + снятие isStale
  dismissStale: () => void; // снять баннер, данные не перечитывать
}
```

`enabled` гасит **только захват, не подписку**: наблюдение нужно и тому, кто блокировку взять не может.

Две детали, которых спека изначально не предусматривала. Освобождение на `beforeunload` уходит `fetch`'ем с `keepalive` — обычный запрос при закрытии вкладки отменяется, а `sendBeacon` не умеет ставить заголовок `Authorization`. И возврат на свёрнутую вкладку продлевает блокировку немедленно: браузеры троттлят там таймеры сильнее, чем 60-секундный TTL, так что к моменту возвращения блокировка уже снята sweeper'ом.

**Момент захвата зависит от страницы.** Там, где есть явный режим редактирования — приёмка, списание, дровер каталога, — блокировка берётся по входу в него, а не при монтировании. Иначе простой просмотр объекта показывал бы коллегам ложное «Редактирует Иванов». У страницы заказа такого режима нет, там захват при монтировании, как и задумывалось.

У инвентаризации режимов тоже два — шапка и выбор ячеек, — а вот **пересчёт блокировку не берёт**: ячейки сохраняются по одной, и несколько человек, считающих разные ячейки одной инвентаризации, — штатный сценарий, а не гонка. Ровно то же рассуждение, что оставило без блокировки экран сборки. Подписка при этом работает, так что изменение состава ячеек другим пользователем перечитывается сразу.

У приёмки и списания режимов редактирования **два** — форма шапки и дровер позиций, — и блокировку держит любой из них. Секция позиций поднимает своё состояние наверх через `onEditingChange`, страница объединяет по «или». Редактирование состава — как раз более длительное занятие, чем правка шапки, и оставлять его без блокировки значило бы пропускать ровно тот конфликт, ради которого она заводилась.

При `isOwner === false` показывается `EditLockBanner` — предупреждение с именем держателя, **без блокировки полей и кнопки сохранения**.

`isStale` поднимается по `entityChanged` или по `editLockReleased` от другого пользователя. Если `isDirty === false`, хук сам вызывает `refresh()` и баннер не показывается; иначе рендерится `StaleDataBanner`. `isDirty` передаётся страницей из `formState` React Hook Form — сам хук о форме ничего не знает.

`useEditLock` используется только на страницах отдельных объектов. В таблицах и списках ни блокировки, ни устаревание не отображаются.

## Первый потребитель: синхронизация маркетплейсов

`MarketplaceSyncService` публикует `marketplaceSyncProgress` после сохранения складов и каждой страницы карточек, `MarketplaceOrderSyncService` — после каждой страницы отправлений, и `marketplaceSyncFinished` по завершении. Все события адресуются `ToWatchers(MarketplaceAccount, accountId)`; сборка события живёт в `Integrations/Sync/MarketplaceSyncEvents.cs` — расширениях над `IRealtimeNotifier`, чтобы обе службы синхронизации не дублировали адрес и payload.

Событие об отказе публикуется **внутри `FailAsync`**: через неё проходят все шесть catch-веток, и это единственное место, где `finished` со статусом `failed` нужно поднять. `ReconcileInterruptedRunsAsync`, помечающий зависшие прогоны на старте процесса, событий не шлёт — открытых соединений в этот момент не существует.

**Подписка идёт на аккаунт, а не на прогон.** `syncRunId` остаётся в payload — по нему клиент отличает прогоны, — но ключом подписки быть не может: клиент узнаёт идентификатор прогона либо из `202` собственного запуска, либо опросом `/sync-runs`. Прогон, начатый планировщиком или другим пользователем, при подписке по `syncRunId` остался бы невидимым — то есть опрос, ради устранения которого всё и делается, пришлось бы сохранить. Идентификатор аккаунта, напротив, известен странице и модалке до запуска, а `MarketplaceAccount` уже есть в `AppEntityType` — заводить значение под сущность, у которой нет своей страницы, не требуется.

Вкладка «Обзор» аккаунта подписывается на свой аккаунт, перестаёт опрашивать `/sync-runs` по интервалу и обновляет счётчики по событию. Модалка массовой синхронизации заказов подписывается на каждый выбранный аккаунт — их идентификаторы известны из `/accounts/order-sync-targets` ещё до нажатия «Синхронизировать».

Опрос остаётся запасным механизмом на случай, когда стрим не установлен: подписка живая → `refetchInterval` выключен, стрим оборван → включается. Пользователь не должен видеть замерший экран из-за проблем с транспортом.

### Реализовано

**Серверная часть шагов 1–6 целиком.**

- `Infrastructure/Realtime/` — конверт и полиморфный payload, `RealtimeEventType`, `RealtimeAddress`, `RealtimeConnection`, `RealtimeConnectionManager`, `EntityWatchRegistry`, `IRealtimeNotifier`/`RealtimeNotifier`. Всё, кроме соединения, — синглтоны рядом с `SecurityVersionStore`.
- `Controllers/RealtimeController.cs` — `GET stream` с keep-alive и закрытием по истечении токена, `POST watch` / `POST unwatch`.
- `ErrorCode.RealtimeConnectionUnknown` (`130` — не `126`: нумерация в enum не по порядку, максимум был `129`).
- Публикация событий синхронизации из обеих служб через `Integrations/Sync/MarketplaceSyncEvents.cs`.
- `IEntityAccessService` (предварительная работа отдельной задачи) — вместе с общей инфраструктурой доступа `Infrastructure/Access/`, на которую переведены `IUserQueryFilterService` и пообъектные проверки во всех контроллерах.

Проверено вживую: `connectionReady` приходит мгновенно, `:ping` ровно через 20 секунд, реальный прогон Ozon даёт три `marketplaceSyncProgress` и `marketplaceSyncFinished` со `status: success`; соединение без подписки не получает ничего; после обрыва стрима `watch` с тем же `connectionId` даёт `422`.

**Клиентская часть шагов 4–6 целиком.**

- `src/contexts/Realtime/` — `RealtimeContext`, `RealtimeProvider` (единственный стрим, собственный цикл переподключения, диспетчер событий, реестр подписок с рефсчётом). Смонтирован в `MainLayout`.
- `src/hooks/` — `useRealtime`, `useRealtimeEvent` (payload сужается по типу конверта), `useEntityWatch` / `useEntityWatchMany`.
- `src/utils/queryKeys.ts` — `byOperation` для инвалидации всех вариантов одной операции, включая пагинированные.
- Потребители: `MarketplaceAccountPage` (подписка на аккаунт, тост по `marketplaceSyncFinished`), `AccountSyncRunsTab`, `SyncOrdersDialog` (подписка на каждый выбранный аккаунт). `refetchInterval` во всех трёх местах остался запасным механизмом и гасится подтверждённой подпиской.

**Шаги 7–10 целиком.**

- `EntityChangedEvents` / `PublishesEntityChangedAttribute`, публикация из `AbstractChangeLogService.CompareAndSaveToChangelog` и из `OrdersController`; `RealtimeAddress.ToWatchers(..., exceptUserId)`.
- `EditLock`, `EditLockStore` (двусторонний индекс по образцу `EntityWatchRegistry`), `EditLockEvents`, `EditLockSweeper`, три эндпоинта `locks/*`, снятие блокировок по обрыву стрима.
- `ErrorCode.EditLockHeld` (`131`), `ErrorCode.EditLockNotHeld` (`132`).
- Клиент: `useStaleData`, `useEditLock`, `EditLockBanner`, `StaleDataBanner`. Блокировку берут страницы заказа, приёмки, списания, инвентаризации, склада и сотрудника, экран ролей, дровер каталога и диалог привязки карточки. Только наблюдение, без блокировки, — экран сборки, пересчёт инвентаризации, дровер ячеек хранения и просмотровые страницы склада и сотрудника.

**Просмотр тоже подписывается.** Формы там нет, `isDirty` всегда `false`, баннер не появляется никогда — хук просто перечитывает данные. Полагаться на фокусный рефетч TanStack нельзя: он срабатывает при возврате на вкладку, а открытая и не теряющая фокус страница показывала бы чужую правку сколь угодно долго.

**Presence.** `EntityPresenceService`, событие `entityPresenceChanged`, `presence` в ответе `watch`; на клиенте
`useEntityPresence`, `EntityViewers` и слот `viewersOf` у `PageGenericHeader`. Аватарки показывают страницы
отдельных объектов, включая просмотровые, и диалог привязки карточки; дровер каталога — только в режиме
редактирования. Экраны со множественной подпиской (сборка, ячейки хранения, модалка синхронизации) presence не
показывают: строка аватарок на каждую строку таблицы — шум, а не информация.

### Где блокировки сознательно нет

Три места берут подписку, но не берут блокировку, и по одной и той же причине — **параллельная работа там штатна или защищать нечего**:

- **экран сборки** — у заказа несколько `AssemblyTask`, несколько сборщиков одновременно норма;
- **пересчёт инвентаризации** — ячейки сохраняются по одной;
- **дровер ячеек хранения** — правки применяются сразу, несохранённого состояния не существует, так что беречь нечего; список просто держится актуальным через `entityChanged` по каждому узлу.

### Роли как коллекция

`RolesListDtoChangelogService` пишет роли **одной записью с `entityId = Guid.Empty`** — они редактируются целиком, а не по одной. Подписаться на такой ключ было нельзя: `CanViewAsync` искал `ApplicationRole` с нулевым id и всегда отвечал `false`.

Решение: пустой id означает «коллекция целиком», и права по нему проверяются разрешением, без поиска строки — `IEntityAccessRule` получил в интерфейс уже существовавший на реализациях `PrecheckAsync`, а `EntityAccessService` ветвится по `entityId == Guid.Empty`. Тот же ключ используют и событие, и подписка, и блокировка экрана ролей.

Существующий `EventsController` (`api/events`) к подсистеме отношения не имеет — он отдаёт события календаря для `@mui/x-scheduler`.

### Отложено

- **Токен конкурентности** — `UseXminAsConcurrencyToken` на редактируемых агрегатах + код `entityModifiedConcurrently`. Пока не реализован, блокировка остаётся уведомительной и конкурентная запись остаётся возможной. Это принятый компромисс, зафиксированный в разделе «Область ответственности».
- **Ужесточение блокировки** — перевод формы в режим только для чтения и проверка блокировки на `PUT`. Имеет смысл только после токена конкурентности.
- **Backplane для нескольких инстансов** — `LISTEN`/`NOTIFY` на PostgreSQL.
- **Разделение стрима между вкладками** через `BroadcastChannel`.
- **Покрытие `entityChanged` за пределами changelog** — сущности без зарегистрированного `IChangeLogService<T>` полагаются на запасной триггер. Расширяется либо регистрацией changelog-сервиса, либо явной публикацией из контроллера.
- **Push-уведомления** при закрытом приложении — другая инфраструктура (Web Push / FCM), пересекается с этой только схемой событий.

## Принятые решения

| Вопрос | Решение | Следствие |
|--------|---------|-----------|
| Транспорт | **SSE** для уведомлений, REST для команд | Типы остаются в пайплайне `@hey-api/openapi-ts`, новых зависимостей на фронтенде нет |
| Блокировки в списках | **Нет**, только на странице объекта | Пакетный эндпоинт чтения состояния не заводится; состояние приходит из ответа `acquire` и события `editLockReleased` |
| Характер блокировки | **Уведомительный** | Форма не переводится в read-only, `PUT` блокировку не проверяет |
| Сигнал устаревания данных | **`entityChanged`** основным, `editLockReleased` запасным | Публикация из `AbstractChangeLogService`; покрытие ограничено сущностями с changelog-сервисом |
| Реакция на устаревание | Автообновление, если форма не изменена; баннер, если изменена | Автообновление изменённой формы стёрло бы введённые данные |
| Адресация объектных событий | **Явная подписка** `watch`/`unwatch` | Право проверяется один раз при подписке; широковещательной рассылки нет |
| Адресация по праву (`ToPermission`) | **Убрана** | Клеймы `permission` на соединении не хранятся; соединение знает только `UserId` и `UserName` |
| Ключ подписки на синхронизацию | **`MarketplaceAccount`**, не `MarketplaceSyncRun` | Ловит прогоны планировщика и других пользователей; новое значение `AppEntityType` не заводится |
| Карта `AppEntityType` → право | **`Services/IEntityAccessService`** | Инфраструктура real-time не знает про домен; там же будущие проверки доступа к конкретному объекту |
| Токен конкурентности | **Отложен** | Конкурентная запись остаётся возможной — принятый компромисс |
| Цикл переподключения | **Свой в `RealtimeProvider`**, а не встроенный в сгенерированный SSE-клиент | Встроенный выходит из цикла при штатном закрытии стрима — а именно так закрывается стрим по истечении токена; заодно бэкофф сбрасывается после каждого `connectionReady` |
| Возврат из фона | **`visibilitychange` + `online`**, без `@capacitor/app` | Одна ветка кода на веб и Capacitor; новых зависимостей нет |
| Флаг устаревания | **Отдельный `useStaleData`**, `useEditLock` построен поверх | Страница с формой, но без права на блокировку (сборщик на заказе), предупреждение всё-таки получает |
| Сброс флага устаревания | **Сравнение `dataUpdatedAt` с моментом события** | `staleTime` нулевой и TanStack рефетчит на фокусе — отдельный механизм сброса не нужен |
| Момент захвата блокировки | **По входу в режим редактирования**, где он есть | Просмотр объекта не показывает коллегам ложное «Редактирует Иванов»; на заказе режима нет — захват при монтировании |
| Публикация `entityChanged` для заказов | **Фильтр `[PublishesEntityChanged]` на контроллере** | У `Order` нет changelog-сервиса; двадцать точек вызова — двадцать шансов забыть одну |
| Истечение блокировки по TTL | **`EditLockSweeper` публикует `editLockReleased`** | Все три способа освобождения выглядят на проводе одинаково |
| Гранулярность `watch`/`unwatch` | **Батч сущностей за запрос** | Экран сборки не открывает по запросу на заказ; `watch` отвечает `200 { watched, presence }`, отказ по правам поштучный |
| Доставка presence | **Полный список в событии**, начальный — в ответе `watch` | Единственное событие, которое является состоянием: перечитывать presence неоткуда |
| Кого показывать в presence | **Только других, дедуп по `userId`** | Свои вкладки не считаются; держатель блокировки виден и в аватарах, и в баннере — они отвечают на разные вопросы |
| Имя пользователя на проводе | **`FullName` из клеймов токена** | Ни похода в БД на соединение, ни логинов в баннерах |

## Открытые вопросы

**Что делать с блокировкой при переходе объекта в статус, где редактирование запрещено?** Например, заказ ушёл в `Shipped`, пока его форму держали открытой. Сейчас блокировка просто истечёт по TTL, но пользователь до этого момента будет видеть форму, сохранить которую уже нельзя.
